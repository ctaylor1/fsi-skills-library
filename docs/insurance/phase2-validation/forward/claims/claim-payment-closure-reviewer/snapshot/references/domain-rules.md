# Native method and limits

A draft payment request is tied to claim/payee/payment identity, amount and currency. Reviewed authority must cover that claim/payee, a limit, approver, approval state and valid date interval. Matching payment identity or the same claim/obligation identity in pending/submitted/settled history is a duplicate blocker, even under a new proposed payment ID. History is a current transaction snapshot with unique payment IDs, source evidence, claim/payee/obligation identity, currency and amount. Complete relevant history requires explicit attestation and source evidence; this is not a live processor idempotency guarantee.

The supported operating gate categories are coverage, payee verification, sanctions, liens, settlement documentation, bank verification and authority. These are configurable operational evidence categories, not a statement that each is legally required in every jurisdiction. A not-applicable gate requires reviewer rationale. Missing, failed or unknown gates block readiness. No screening or bank verification is performed by this package.

Closure separately matches required_payment_ids (including the reviewed request) to settled claim transactions and ties the request to payee, obligation, currency and amount. A new unpaid payment can be ready for payment review while closure is blocked. A settled transaction can support closure review while repeat payment is blocked. Closure additionally requires an explicit empty obligation list, reviewed zero remaining case reserve and reopening triggers with ownership. The amount is a supplied operational balance, not automatically a proposed reserve release. Open recoveries, litigation, expenses, communications, complaints or record obligations must be represented when relevant. The output can be ready for authorized review; approval and execution still remain separate. The helper does not execute payment, close/reopen a claim, release reserves or send notices.
