## Finding: undocumented revision string requirement

Initial input used natural JSON numeric revision labels 1 and 2. The native schema says every reading includes revision but does not specify a string type there. Its general numeric guidance allows integer JSON numbers. Input validation reports valid=true, yet the calculation reports “revision is unresolved” for both supplied labels and nulls otherwise evaluable arithmetic. An explicitly supplied revision can therefore be mislabeled missing without actionable type guidance.

The recovery changes R1's local original-reading designation to text `original` and R2's supplied revision number to text `2` (Y1 likewise `original`). No source numeric values, lineage, finality, scope or monetary terms change. The same clarified baseline then becomes ready-for-review with the correct USD 30,000 provisional scenario. The earlier integer-label runs and exact input copies are retained. Recommendation: state a nonempty text type in the schema, provide numeric-identifier normalization guidance, and make the diagnostic name the type requirement. This is an interoperability/usability finding; the observed behavior fails closed.

The first R1 revision number 1 and Y1 revision number 1 were local mapping assumptions, because original reading revision numbers were not explicitly supplied. They are not treated as authenticated facts; recovery uses original labels. See source-mapping-notes.md for the complete transformation record.
