# Wealth performance method and input contract

Build a household/account performance report from valuations at every cash-flow boundary. This is cumulative time-weighted reporting under the explicit flow and fee conventions below; it is not an annualized return, money-weighted return, attribution model or claim of GIPS compliance.

## Specific fields

- `currency: USD`, nonempty `accounts: [{account_id, source_ids}]`, and `report_period: {start, end}` with start before end and end no later than `as_of`.
- `methodology`: `version`, `owner`, `method: flow-boundary-twr`, `fee_timing: end-of-subperiod`, explicit boolean `all_flows_at_boundaries`, nonnegative `return_tolerance_bps`, `source_ids`. False boundary coverage suppresses returns; obtain the missing flow-boundary valuations.
- `subperiods`: `{period_id, start, end, accounts}`. Intervals are (start, end]; the next start equals the previous end, with no gaps or overlaps. Each account row has `account_id`, `source_ids`, and cents fields `opening_value`, `ending_value`, `external_flow_start`, `external_flow_end`, `internal_flow_start`, `internal_flow_end`, `fees_end`. Values and fees are nonnegative; flows are signed, positive into the account. Fields may be null to retain missingness. A missing field is never zero. Every declared account must appear in every subperiod. Opening values must equal previous closing values before new start flows.
- `official_reference`: `household_end_value`, `household_net_return_pct`, `source_ids`. Amounts are cents; returns are percent, e.g. 5 means 5%. Values may be null, resulting in reconciliation gaps. This independently supplied reference is not proof of source authenticity.
- `benchmark`: `applicable` boolean and `source_ids`. If false, supply a substantive `reason`. If true, supply `benchmark_id`, `version`, `rationale`, `currency`, `returns: [{period_id, return_pct, source_ids}]`. Returns are percentages at least -100 and must exactly match the portfolio periods and currency.

## Arithmetic and interpretation

For each account and each valued subperiod, capital = opening value + start external flows + start internal flows. Net factor = (ending value − end external flows − end internal flows) / capital. Gross factor adds `fees_end` to that numerator, assuming the fees were deducted at the end of the subperiod. Mid-period fees need an additional boundary or another approved method. Capital must be positive and the net residual nonnegative; unsupported periods remain unevaluable. A fully known account with every value, fee and flow equal to zero has no applicable subperiod return and does not invalidate household returns. Its cumulative return links only active periods; an account never invested has null cumulative return, explicitly not applicable.

Multiply subperiod factors, subtract one and multiply by 100 for cumulative percent returns. For the household, sum account values/flows before computing the period factor; never average account percentage returns. Internal transfers must offset separately at start and end. A cross-boundary transfer with cash in transit requires explicit valuation/account evidence; do not drop it. Round reported returns to six decimals, monetary results to cents, half-even. Calculation uses unrounded factors.

Missing rows/fields, unsupported flow timing, broken valuation continuity or interval coverage suppress the affected cumulative returns. The ending value can still be observed when all closing values exist. `observed_fees` and `observed_net_external_flows` cover complete rows only and are partial whenever financial row coverage is incomplete. Source gaps preserve diagnostic calculations but make the artifact needs-data. Compare ending value exactly and net return within the supplied tolerance (1 percentage point = 100 basis points). Compound benchmark factors over the same periods; the reported active spread is net percentage points, not contribution or alpha.

The two-period example has net household factors 1.0990625 and 1.05: cumulative net 15.4015625%, displayed 15.401562%. Gross is 15.5%; ending value is $179,392.50. An 8% then 4% benchmark compounds to 12.32%. Fees total $150 and household net external flows total $5,000.

## Common input and evidence

Use the complete synthetic [request](../evals/files/request_example.json) as the serialization example. Required top-level fields are `schema_version: wealth-p0-v1` (the retained envelope version, not the delivery wave), `request_id`, `household_id`, ISO `as_of`, `engagement` with explicit `capacity` (advisory, brokerage, private-bank, or trust), `engagement.jurisdiction: US`, and nonempty `sources`. Each source has unique `source_id`, `reference`, `owner`, `as_of`, `valid_until`; its window must cover the request date. Source identifiers on evidence are `source_ids: [id, ...]`. Source metadata establishes traceability, not truth or authority. Registry date defects reject the request; missing item citations remain findings.

`unresolved_issues` is an explicit list of objects with `code`, `message`, `source_ids`; copy known upstream concerns unchanged, using `[]` only after substantive review. Every input row identifier is a unique nonempty string within its list; referenced accounts/lots must exist. Dates are exact ISO calendar dates. Monetary inputs accept finite decimal strings or JSON numbers, excluding booleans; money has at most two decimal places where specified, quantities/rates at most eight. No FX conversion, missing-to-zero conversion, short positions, or automatic source retrieval is implemented. Input structural validation is necessary but the calculation also performs financial consistency checks.

The output is the shared draft envelope: input hash and artifact ID, scope, sources, findings, status, full `result.input_snapshot`, and calculated evidence. Any finding means `needs-data`; `review-ready` means the structured artifact has no detected gaps, not professional acceptance. Output validation recomputes the entire artifact, including financial values and findings, from that snapshot. An attacker who changes both input and output consistently can produce a new valid draft; hashes are not signatures or an approval record.
