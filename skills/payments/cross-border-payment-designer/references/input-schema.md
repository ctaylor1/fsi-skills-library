# Corridor native input

Use the foundation 1.0 JSON envelope: request_id, as_of ISO date, jurisdiction (payer origin), participant, requested_action analyze/draft, sources with source_id/reference/as_of and optional review_due, upstream_issues, data. All source_ids must reference registered sources. All money values are decimal strings; null denotes unknown where allowed. No raw credentials.

`data` requires `use_case` consumer-remittance/commercial-payment/correspondent-transfer; positive `principal` in payer currency; timezone-aware `evaluate_at`; `accountable_reviewer`; `payer` and `payee` each with entity_id, account_ref, jurisdiction and currency; `options` list. Supported pairs are US/USD, EA/EUR, UK/GBP, BR/BRL, IN/INR and CA/CAD. Origin and destination differ. This is a bounded corridor scenario contract, not support for every activity between those places.

Each option requires unique option_id, source_ids, charge_convention (OUR/SHA/BEN/not-applicable/unknown), charge_convention_review_ref, fees_complete boolean, expected_delivery_review_ref, fees, legs, regulatory_reviews and sanctions_review. Missing review references remain gaps; no review is synthesized.

- `fees`: unique fee_id, kind fee/tax, charging_entity, jurisdiction, currency, amount decimal or null, side payer-addition/principal-deduction/recipient-deduction. The first two sides use payer currency, the last recipient currency. An empty complete inventory asserts no fees and must be independently evidenced; incomplete inventory makes both totals unknown.
- `fx_quote`: null or base_currency, quote_currency, positive rate (quote units per one base unit), quoted_at, expires_at, kind firm/indicative and quote_ref. Cross-currency without a quote leaves receipt unknown. Expired/indicative quotes can show scenario arithmetic but prevent comparison readiness.
- `legs`: leg_id, unique economic_id within option, purpose customer-collection/correspondent-delivery/local-payout/nostro-funding, from_entity, from_account_ref, to_entity, to_account_ref, jurisdiction of that leg, currency, amount or null, method, obligation_ref, access_review_ref, funding_review_ref, timing_review_ref. Each option has exactly one customer collection and final local payout; stage identities are distinct. Non-funding legs appear in delivery order; each after the first requires previous_leg_id and its from_entity equals the preceding to_entity. A change from the preceding destination account to the next source account requires account_transition_review_ref. This records the reviewed internal account/currency transition rather than assuming account money is interchangeable. A funding movement is a separate leg, never additional customer principal. All intermediary entities and jurisdictions must be included in screening scope.
- `regulatory_reviews`: one per involved jurisdiction, with jurisdiction, use_case, reviewer, reference, rule_version, activity_scope_ref, entity_ids covering the entities involved in that jurisdiction, aware valid_from/valid_until. These record supplied specialist review, not machine legal conclusions.
- `sanctions_review`: exact entity_ids and jurisdictions sets across all legs plus both parties; reference, reviewer, policy_version, aware valid_from/valid_until. No actual list screening occurs.

Totals: payer debit = principal + payer additions. FX input = principal - principal deductions. Expected receipt = FX input × recipient units per payer unit - recipient deductions. Inverse quotes are divided; no rounding policy is assumed. Negative receipt or deductions above principal are unresolved. OUR with deductions or BEN with additions is an allocation conflict. SHA is not treated as proof of any fee amount.

Customer collection must equal payer debit and final payout must equal expected receipt with exact party/account/currency binding. No unsupported raw MT/ISO payload, UPI collect, Pix automatic debit or Interac international adapter is accepted implicitly.

Intermediary conservation is native: each correspondent-delivery leg must equal principal minus all principal deductions in payer currency, or that same principal converted using the quoted rate in recipient currency. Recipient deductions occur at final payout. The output retains declared/expected amount and difference per intermediary. Other intermediate currencies, partial/split intermediary legs or stage-specific fee deduction schedules need a separate expanded contract and cannot become comparison-ready here. Nostro funding remains separately modeled and never adds customer principal.
